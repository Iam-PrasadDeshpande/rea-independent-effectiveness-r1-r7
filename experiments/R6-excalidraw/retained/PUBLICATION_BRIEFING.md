# What a whiteboard reconstruction tells us about reverse-engineering agents

An agent that can describe an application has not necessarily understood enough to rebuild its behavior. I wanted this evaluation to keep those two claims separate: what the agent could explain, and what its submitted software could actually do.

The target was a locally built, pinned production-mode version of Excalidraw. That gave the evaluation a real React application with canvas interaction, browser persistence, history and downloadable exports. It also gave the evaluator an exact source revision for checking claims. The investigators received the packaged application and permitted inspection tools, while the source, source maps, hidden tests and other investigators' work were withheld. This establishes a controlled local target; it does not establish that a model had never encountered Excalidraw before training.

Three fresh Codex sessions attempted the same bounded workflow. The first had ordinary browser and asset inspection. The second also had direct CDP and AST tools available, although its retained trace shows CDP use and no AST invocation. The third had REA browser tools in addition to the common inspection tools. Each session had the same model, effort and stated action and time ceilings.

Before those sessions began, two reference runs agreed on 36 normalized behavioral cases. The evaluator then ran all 36 cases against each sealed reconstruction. The ordinary-inspection submission matched 3 cases, the direct-tool submission matched 30, and the REA-assisted submission matched 27. The first result needs context: the submitted JavaScript had a syntax error, and its three matches were empty-scene stability checks. They do not demonstrate a functioning drawing application. The other submissions performed substantially more of the bounded workflow, but both differed from the reference. The direct-tool submission missed line, free-draw, text and grouping cases. The REA-assisted submission also failed the tested export UI paths. Font measurements, geometry and interaction details remain important even when an implementation looks plausible.

REA did successfully inspect the real browser application and retain identifiable evidence. A separate capability preflight also analyzed captured production scripts with its installed parser. That is a concrete capability result. It is not proof that the investigator recovered the application's complete architecture or used every captured script effectively.

The operational boundary mattered. A REA page inspection returned about four million characters, exceeding the model transport's one-million-character message limit. The response was retained, but it could not be delivered in full to the investigator. A same-session recovery continued the work, and the agent submitted code, but a later execution error prevented its final architecture report. The recovery also exposed a timezone defect in elapsed-time accounting. Actual timestamps establish that the observed run stayed within 30 minutes, but the faulty guard prevents a claim that equivalent time enforcement was fully proved. Those are evaluation and integration limitations, not evidence that REA is inherently worse.

The separately graded architecture reports were more informative for the direct-tool arm than the ordinary-inspection arm. The REA-assisted arm had no final architecture report to grade. Its missing report is an evidence gap; treating it as proof that REA discovered nothing would be misleading. Likewise, fewer reported tokens from an interrupted investigation cannot establish a cost advantage.

This run did not demonstrate an incremental REA advantage over direct tools. It also did not support a clean causal comparison: there was one sequential run per arm, uneven completion, transport recovery and a timing-control defect. The useful enterprise lesson is about the evidence chain. Capturing runtime evidence, delivering it within the agent's context budget, recovering the important relationships and producing working software are separate engineering outcomes. Each needs its own verification.

These are private evaluation findings, not a claim of full application reconstruction, production readiness, universal tool superiority or general cost savings. No publication is authorized or performed.
