Disposition: PASS_WITH_GAPS for a bounded, source-derived JVM reconstruction experiment. This review does not qualify source-to-APK reproducibility, real Room persistence, Android reminder delivery, or generalized REA superiority.

Scope: Reviewed the signed arm controller, frozen public prompt/contract, evaluator Oracle.kt and generator, relevant source recurrence/mutation/query/reminder/deletion methods, provenance records and frozen manifest. ## Isolation and comparison

The model is a fresh Codex session driven with user config ignored, project documentation disabled, memories disabled, network disabled and built-in tool feature families disabled. Responses are structured literal actions; the signed controller exposes only per-arm catalogs, synthetic compilation and arm-local query logs. Source, oracle and peer results are absent from the explicit prompt. No hidden tests feed back into the sessions. This is a controlled dispatcher design with application-level tool isolation. The Codex host process itself is not started inside the bubblewrap source-excluding mount namespace, so do not describe every investigator process as OS-isolated from all evaluator files. Final event-log verification is necessary to confirm that disabled built-in tools were not invoked; the controller rejects forbidden events after receiving a turn.

Untrusted Java compilation/execution does use bubblewrap --unshare-all, cleared environment, read-only JDK/tool/system mounts and one arm-local output mount, with no source/evaluator/peer mount or network namespace access. Provider processes run under the signed host dispatcher with restricted action names; they are not themselves in that namespace. Distinguish these boundaries in reporting.

Direct and REA select the same pinned headless JAR with one worker, full resources, 1536MiB heap and two active processors. REA's bridge/provenance/evidence-view layer is the treatment. Catalogs differ deliberately: direct permits class source, strings and broader searches; REA permits typed method/class inspections and retained evidence views. Equal query ceilings therefore equal interaction counts, not equal underlying operations, output bytes or information opportunity. Report tool calls, output paging and actual observations alongside correctness. The 24,000-character first-page cap and charged read_log calls can make REA's larger envelopes consume more query budget.

Material confound: all arms run concurrently on a shared host. Time includes indexing/setup and model latency; REA additionally evicts its retained JADX process after60s idle. This can add treatment-specific reload work. Latency differences cannot establish speed improvement or regression from this run. One trial per arm also cannot establish repeatable model-level superiority. No explicit model/version pin appears in Run-R5Arm.ps1 argv; retain each session's actual model metadata and qualify comparison if resolved versions differ or metadata is unavailable.

## Oracle fidelity and limits

The core Event implementation and four recurrence/edit/delete-one methods are source-extracted. Independent spot checks found the source-consistent behaviors needed for the public contract: weekly daily-candidate stepping; Monday-anchored multiweek filtering; signed count/until limits; count consumed before exception filtering; overlap-inclusive range selection; day-code parent exception plus detached nonrepeating child; and preserved original exception date when moving a child. The adapter's integer date-code string parsing preserves the expected eight-digit dates for the frozen modern-year scenarios. No material expected-output error was identified in the inspected bounded scenarios.

The reminder recorder matches source Context.scheduleNextEventReminder's reverse stored order, strictly-future test, next occurrence/request selection, nominal YEAR horizon and +1000ms, with EventActivity's ascending minute normalization applied before storage. It recomputes the final planned requests rather than recording the sequence of scheduling/cancellation operations. Host.scheduleNextEventReminder is a no-op (Oracle.kt288); the source calls inside edits/deletes consequently produce no intermediate alarm evidence. This cannot establish cancellation, pending-intent replacement, receiver delivery/rescheduling, permission correctness, AlarmManager behavior or notification display. Duplicate or missed intermediate requests can remain invisible even when final arrays match.

Persistence is a Gson round trip of in-memory rows (Oracle.kt481). It tests serialization survival of the reconstruction state, not actual EventsDao/Room SQLite transactions, schema converters, migrations, failure recovery or restart integration. Source exception persistence is inspected independently, but is not executed through Room.

Series deletion is h.rows.clear() (Oracle.kt480). Because the public contract has a single initial root and its detached children, clearing produces the expected state for that bounded population. It does not execute or test recursive parentId deletion, preservation of unrelated series, database delete failures or pending-intent cancellation. A passing deleteSeries scenario supports this one-root observable result only.

Initial creation directly adds the event row (Oracle.kt476), whereas actual EventsHelper.insertEvent validates startTS<=endTS and triggers scheduling. Invalid initial ranges, malformed inputs, unsupported reminder types, completed tasks, CalDAV, all-day events and invalid/corrupt persisted data are not qualified by this contract. Do not generalize the architecture's error-handling inventory into tested error-handling correctness. A moved edit changes start and end independently under the contract; its adapter reconstructs omitted end from original occurrence duration before applying changes, so this is a contract-level field operation, not proof of every date-editor gesture's automatic end adjustment.

44 cases satisfy the requested minimum with varied recurrence, mutation, overlap, scheduling and date boundaries. Case17 empty weekdays is a low-level robustness probe and must be separated from the43 nominal user-reachable cases. The public contract exposes source-neutral operation names and output projections, but also narrows the feature to one root, up to3 nonnegative reminder offsets, final-state queries and planned requests; it is not a reconstruction of the complete Android application.

## Permissible final conclusions

Report exact frozen-oracle correctness separately from architecture rubric support, tool invocation success, observation provenance, limitations and cost. A valid treatment prerequisite has real REA package/method inspection evidence. A better oracle score can demonstrate improvement in this single bounded controlled run; it cannot establish general REA effectiveness, real Android feature equivalence or source/APK reproducibility. Retain UNKNOWN/NOT_TESTED for Android notification delivery and Room persistence. Compare direct JADX to REA explicitly and explain output/caching/setup costs instead of claiming a wrapper accuracy gain from presence alone.

## Pilot recovery update

The controller owner reported a Windows-to-WSL stdin encoding defect: Unicode APK badging caused invalid UTF-8 at the investigator CLI. This audit did not inspect pilot outputs. Explicit UTF-8 on all redirected process streams is a justified harness repair. Retain original pilots, controller signatures/hashes/manifests and the failure evidence; classify them as pilot setup/recovery overhead, not valid final-arm performance. Before matched restart, re-sign the repaired controller and freeze its new hash, then give all three arms fresh independent sessions under the repaired controller. Freeze timestamps should distinguish the original oracle/prompt freeze from repaired transport-controller freeze. Repeating all three arms avoids selectively retrying a disadvantaged arm, but shared-host timing and one-run uncertainty remain. No extra oracle or prompt changes are warranted from this transport failure. Total audit tool invocations:8, including this append.
